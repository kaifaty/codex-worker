## How to work

- Work only in this worktree, on branch `{branch}`. Do not touch other branches, worktrees, or repositories. Follow the repository's `AGENTS.md` or `CLAUDE.md`, if present.
- No protocols, manifests, audits, or intermediate reports. Do not create subagents to read reports.
- Run checks for this task only: build and test the affected module, plus one suitable benchmark or end-to-end test. Do not run the full regression suite unless the task explicitly asks for it.
- If a check (test environment, test, or end-to-end test) fails twice after changes, stop with `status: "blocked"`, the numbers, and what you tried. Build and lint errors while writing code do not count as checks: fix them and continue. A failure that also happens on a clean `{base}`, or that passes when rerun once without changes, is not the task's: do not count it as an attempt or fix it; name it with the numbers in the result and `pr_body`, and continue. Check a clean `{base}` in a temporary `git worktree` that you remove afterwards, not with a stash. If the task is the test environment or scenario itself, debugging its setup (positions, synchronization, signals) is also part of the work; stop when the actual mechanism fails twice with the setup correct.
- If continuing requires a decision missing from the brief, do not guess. Finish with `status: "needs_decision"` and put the question in `questions`.
- Commit as you go. At the end, push the branch; do not open or edit PRs yourself. The supervisor publishes the PR against `{base}` from `pr_title` and `pr_body` in your result. Do not merge the PR or deploy anything: Claude handles review and merging.
- Do not include Co-Authored-By or "Generated with" lines in commits, PR titles, or `pr_body`.
- Include the required string fields `pr_title` and `pr_body` in the result. Write the description of the whole PR, not just this turn, in `pr_body`; an empty string means leave an existing PR unchanged. Set the compatibility field `pr` to an empty string.
- Include `commit_message` as a string in the result: use an empty string if you committed the changes yourself or there is nothing to change. When leaving changes for the supervisor to commit, follow the repository's commit-message rules and put the subject on the first line.
- Finish with JSON matching the supplied output schema. Set `status` to `done` only when every "Done when" condition is met, `partial` when some work is complete and can continue, `blocked` when an external change is required or after two failed attempts, or `needs_decision` when a required decision is missing from the brief. Write a short plain-English `summary`; include `checks` with `command`, `outcome` (`passed`, `failed`, or `not_run`), and `details` containing numbers; list questions for Claude in `questions` and unfinished work in `remaining`. In a review-fix turn, include each finding in `findings` with its `id`, `decision` (`fixed` or `rejected`), and a short `note`; give rejected findings a one-line reason. In an ordinary turn, use an empty `findings` array. Use empty arrays when there are no checks, questions, or remaining work.
